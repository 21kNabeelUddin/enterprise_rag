Enterprise RAG Pipeline

From a folder of company documents to a cited answer. There are two pipelines and one shared storage layer. Ingestion prepares the knowledge ahead of time, and the question pipeline uses it on every request.

Are ingestion and querying separate? Yes.

Document ingestion runs offline. A document is loaded, parsed, split into chunks, embedded and written to storage. That happens when the document is added and again when it changes. It does not wait for a user, and a user's question never triggers it.

In the reference diagram, the arrows run from the Encoder and Retrieval into Document ingestion. That reads like "after the query is encoded, ingest documents", which is not a real runtime step. The diagram most likely packs both pipelines into one picture, so ingestion sits next to the storage it fills and is linked to the Encoder because ingestion uses the same embedding model. The arrow is best read as "both sides share a model". It does not describe the order things happen in.

Two parts of that picture do happen at query time. History storage and Feedback storage are written after each answer. They record the conversation and are not document ingestion.

Two processes, one meeting point

The top lane runs on its own schedule. The bottom lane runs on every question. They meet in storage and in one shared choice, the embedding model.

What they share

Storage. Ingestion writes embeddings, text and metadata. The question pipeline only reads them, apart from saving history and feedback.

What must match

The embedding model and its version. If chunks and questions are embedded by different models, their vectors are not comparable and search returns poor matches.

When each runs

Ingestion runs when documents change, usually as batch or background jobs. The question pipeline runs on every request, and each step adds to the response time.

Pipeline 1: document ingestion

Runs offline, once per document and again whenever the document changes. Nothing in this pipeline depends on a user question.

  1. 1

    Data sources and connectors

    Pull documents from wikis, file shares, drives, ticket systems and databases. Keep each document's ID, source URL and last-modified time so changes can be detected later.

  2. 2

    Parse and extract

    Turn PDFs, Word files and web pages into clean text. Keep headings, lists and tables, and run OCR on scanned pages.

  3. 3

    Clean and guard

    Remove boilerplate and duplicates. Scan for malware, and detect or redact personal data and secrets according to your policy before anything is stored.

  4. 4

    Chunking

    Split each document into pieces that are small enough to embed and still make sense on their own. Splitting along headings and paragraphs works better than cutting at a fixed length. A few hundred tokens per chunk with a small overlap is a common starting point.

  5. 5

    Add metadata

    Attach the document ID, title, section, URL, owner, version and the groups allowed to read it (the ACL). This powers filtering, citations and later updates.

  6. 6

    Embedding model

    Convert every chunk into a vector. Record the model name and version with each vector, because the question side has to use the same one.

  7. 7

    Write to storage

    Vectors go to embedding storage (a vector index). Chunk text and source files go to document storage, and metadata and ACLs sit alongside. A keyword index can be added for hybrid search.

  8. ↻

    Re-index trigger

    A webhook, a schedule or a file-hash comparison starts the pipeline for new, changed or deleted documents, so the whole corpus is not reprocessed each time.

Pipeline 2: from question to answer

Runs on every question. Steps are numbered in the order they happen. The top row reads left to right and the bottom row reads right to left, ending at the final response on the left.

  1. 1

    User input

    The question arrives from the chat interface or an API.

  2. 2

    Authenticate

    Sign-in (SSO or tokens) identifies the user and their groups. Those groups are used later to filter what retrieval may return.

  3. 3

    Input guardrail

    Check for prompt injection, jailbreak attempts, personal data and policy violations, and apply rate limits.

  4. 4

    Expected input?

    A router decides whether this is a question the system should answer. If not (small talk, off-topic or blocked), it returns a fallback reply and stops. No retrieval happens.

  5. 5

    Query rewriter

    Uses the chat history to turn a follow-up such as "and the price?" into a standalone question. It can also split a complex question into sub-queries.

  6. 6

    HyDE (optional)

    An LLM writes a short hypothetical answer, and that text is embedded instead of the question. It can help when questions are short or vague. It adds an LLM call, so many systems skip it.

  7. 7

    Encoder

    Embeds the query with the same model that embedded the chunks at ingestion.

  8. 8

    Retrieval

    Searches the vector index, often combined with keyword search. Results are filtered by the user's groups and any metadata filters, and the top candidates (for example 20 to 50) come back.

  9. 9

    Rerank

    A reranker reads the question and each candidate together and scores them more precisely than vector similarity can. Keep the best handful, for example 5 to 10.

  10. 10

    Context builder

    Assemble the prompt: instructions, the selected chunks labelled with source IDs, and recent chat history, all within the model's token budget.

  11. 11

    Generator

    The LLM answers from the supplied context and cites its sources. If the context does not contain the answer, it should say so.

  12. 12

    Output guardrail

    Check that the answer is supported by the retrieved text, contains nothing the user should not see, and follows policy. A failed check triggers a retry or a safe fallback.

  13. 13

    Format answer

    Add citations and links, apply formatting, and stream the text to the user.

  14. 14

    Final response

    The user sees the answer. The turn is saved to history storage, and thumbs up or down feedback goes to feedback storage.

Observability sits across all fourteen steps. Log a trace per request with timings, token counts, the chunk IDs that were retrieved and every guardrail decision, so a bad answer can be traced back to the step that caused it.

Keeping both sides in sync

Because the two pipelines only meet in storage, most production problems come from the stored data drifting away from the source documents or from the query side.

The embedding model changes

Re-embed every chunk. Build the new index next to the old one, switch queries over once it is complete, then remove the old one.

A document is updated or deleted

Remove its old chunks by document ID before adding the new ones. Without this, answers can quote text that no longer exists.

Permissions change

Update the ACL metadata on the stored chunks and filter by it during retrieval. Filtering inside the prompt is too late, because the model has already seen the text.
