0. GROUND RULES FOR THIS LOG
================================================================================

0.1 B0 is immutable. Every optimization gets a new entry (E1, E2, ...) with the
    exact command, n, before/after values and the raw JSON filename.

0.2 Compare like with like: same machine, same models, same corpus, same
    question set, same guard/rerank settings. A change measured on a different
    question set is not a valid before/after comparison.

0.3 Keep the raw JSON. A summary in this file is not enough to defend a resume
    claim; the artifact is the evidence.

0.4 Always report n. A mean from 5 runs is an indicator, not a production SLA.
    With n < 20, the p95 is effectively the maximum observation.

0.5 "n95" is not a standard RAG metric. This log assumes it means p95 latency
    (95th percentile). If you meant NDCG@10 (ranking quality), that is metric
    A5 below.

0.6 Formulas used in every entry:

      latency reduction %      = (before_ms - after_ms) / before_ms * 100
      throughput gain %        = (after - before) / before * 100
      accuracy change (pp)     = after_percent - before_percent
      relative accuracy change = (after_percent - before_percent)
                                 / before_percent * 100

    Example: 26,714 ms -> 24,000 ms is a 10.2% latency reduction.
    Example: 66.7% -> 100% is +33.3 pp (but +49.9% relative).

0.7 A latency win only counts if the quality guardrails for that experiment do
    not regress: answer rate, refusal accuracy, grounding pass, citation
    validity. Record both speed and quality in the same entry.

0.8 Never quote "X% faster" without the raw before/after values and n.

================================================================================
5. KNOWN DEFECTS AND LIMITATIONS AT B0
================================================================================

D1  No-answer detection is phrase-exact.
    File: src/rag_query/domain/citations.py (_NO_ANSWER_MARKERS)
    Example: "What is Apple's share price right now?" produced a correct
    semantic refusal ("I couldn't find the current stock price ... in the
    provided filings") but status stayed ANSWERED because the wording did not
    match a marker. Effect: refusal_accuracy is understated at 66.7%.
    Planned fix: broaden the marker/regex check, then re-run the same eval.
    This is a status/metric fix, not a model-quality improvement; describe it
    honestly in any resume bullet.

D2  No gold question set for answer correctness or retrieval ranking.
    The 12-question eval measures system behaviour (answer/refuse/block) and
    grounding, not factual correctness. NDCG/MRR/EM/F1 remain unmeasured until
    a small qrels/answer key is added.

D3  Small samples.
    n=5 for the full benchmark, n=10 for retrieval-only, n=6 answerable for the
    eval. p95 values are effectively maxima. Increase repeat counts before
    quoting p95 in a resume or README.

D4  Generation dominates latency.
    Any meaningful end-to-end improvement must reduce generation time or hide
    it with streaming. Optimizing retrieval alone cannot move E2E by more than
    a few percent. State this explicitly when reporting cache gains.

D5  Reranker dominates the retrieval-only path.
    1,541 ms mean = 83.5% of the 1,846 ms retrieval path. Retrieval and encoding
    are already cheap (207 ms + 56 ms).

D6  Output guard is the second-largest non-LLM cost.
    548 ms in the controlled benchmark, 853 ms mean on answerable eval runs.
    A grounding-embedding cache can cut this, but must preserve the guard.

D7  Cold start is ~116 s.
    Mostly model loading and index fingerprint check; reranker warmup alone is
    9.3 s. Report cold start separately from query latency.

D8  B0 artifacts do not include token counts or cache stats.
    AskResult already exposes generation.prompt_tokens/completion_tokens, but
    eval_results_baseline.json predates capturing them. Add this to the first
    instrumentation change so tokens/query and tok/s become measurable.

ENTRY E1 | 2026-10-19 | Broaden no-answer detection (D1)
--------------------------------------------------------------------------------
 Hypothesis:
   The model's refusal wording varies ("I couldn't find the current stock
   price of Apple Inc. (AAPL) on the NASDAQ in the provided filings"), and the
   exact-marker check misses it. Broaden detection and make the terminal status
   reflect a partial/no answer even when supporting citations are returned.

 Change:
   - src/rag_query/domain/citations.py
       normalise whitespace; add refusal-shape regexes for "couldn't/could not/
       can't/unable to find ... in the provided filings|context|documents",
       "not found/provided in ...", "the filings do not contain the answer",
       "the answer is not provided in the context".
   - src/rag_query/nodes/format.py
       is_no_answer() now sets NO_CONTEXT regardless of citations; the answer
       and its supporting sources are still returned.
   - tests/test_rag_domain.py, tests/test_query_rag.py
       add variant wording + partial-answer/citations cases.
   - Config/behaviour: unchanged; no model or retrieval change.

 Command / n / question set:
   .\.venv\Scripts\python.exe scripts\eval_rag.py --out eval_results_e1.json
   same 12 labelled questions as B0.

 Performance before -> after (not attributed to E1):
   answerable mean: 28,065 ms -> 25,853 ms (-2,212 ms, -7.9%)
   all 12 mean:     17,035 ms -> 15,101 ms
   refusal path:    11,398-11,738 ms -> 7,520-8,693 ms
   These are run-to-run variance / shorter refusal text, not a code speedup.
   E1 does not change retrieval or generation.

ENTRY E3 | 2026-10-19 | Prompt/KV cache A/B on a repeated query
--------------------------------------------------------------------------------
 Hypothesis:
   llama.cpp reuses the longest cached prompt prefix. For a repeated identical
   RAG query the whole ~5,040-token prompt should hit, so prompt-evaluation time
   should collapse while decode time is unchanged. A brand-new prompt should
   get little or no reuse.

 Change:
   - No retrieval/generation algorithm change.
   - RAG_LLM_CACHE_PROMPT (added in E2) is sent explicitly as ``cache_prompt``.
   - scripts/bench_prompt_cache.py: repeat-query probe reporting wall, generate,
     prompt-eval, cache hit and decode throughput per run.
   - App restarted once with RAG_LLM_CACHE_PROMPT=false and once with true; the
     llama.cpp server (and its KV cache) was kept running across both.

 Command / n:
   .\\.venv\\Scripts\\python.exe scripts\\bench_prompt_cache.py `
       --query "What are Amazon.com's main risk factors in 2020?" `
       --repeats 3 --label cache-off --out prompt_cache_off.json
   (same command with --label cache-on --out prompt_cache_on.json)
   Amazon was chosen because no earlier eval/benchmark used it, making run 1 a
   genuine cold prompt.

 Measurements (5,040 prompt tokens; completion 604-681 tokens):
   config / run             cache hit   prompt eval   generate    wall
   -------------------------------------------------------------------------
   off, 3 runs (mean)          0.0%      3,631 ms    20,982 ms   32,368 ms
   on, run 1 (cold)            0.0%      3,474 ms    22,689 ms   41,077 ms
   on, runs 2-3 (warm mean)   99.9%        148 ms    19,667 ms   26,531 ms

   Warm vs cache-off:
     cache hit:        0.0% -> 99.9%           (5,036 / 5,040 tokens reused)
     prompt eval:  3,631 ms -> 148 ms          (-3,483 ms, -95.9%)
     generate:    20,982 ms -> 19,667 ms       (-1,315 ms, -6.3%; noisy)
     wall:        32,368 ms -> 26,531 ms       (-5,837 ms, -18.0%)
     wall median: 29,711 ms -> 26,531 ms       (-3,180 ms, -10.7%)

 Interpretation:
   The prompt-eval saving is direct and repeatable: 4 tokens evaluated instead
   of 5,040. The end-to-end saving is smaller and has high variance (n=3 off,
   n=2 warm; one warm decode run was an outlier at 25.8 tok/s), so quote the
   -95.9% prompt-eval result and only ~11-18% end-to-end for repeated queries.
   A new prompt gets no meaningful reuse (cold hit 0%), so this is not a
   cold-query speedup. The E2 eval's 99.9% was the same effect after re-running
   the same question set against a long-lived server.

 Quality guardrail: all probe runs answered with 12 citations; no prompt,
   retrieval or guard setting changed. No full eval was needed for this A/B.
 Raw artifacts: prompt_cache_on.json, prompt_cache_off.json
 Verdict: keep cache_prompt=true as the default; report it as a repeat-query
   optimization, not as a general latency reduction.

BACKLOG - candidate experiments (hypotheses, not measured results)
--------------------------------------------------------------------------------
 E1  Broaden no-answer detection  -> DONE (see ENTRY E1)
     Result: refusal accuracy 66.7% -> 100%, overall behaviour 91.7% -> 100%.
     Latencies unchanged within run-to-run variance; answerable questions stayed
     answered. This was a status/metric fix, not model quality.

 E2  Instrument prompt/KV cache and token usage  -> DONE (see ENTRY E2)
     Result: cache_n/prompt_n/prompt_ms/predicted_ms parsed into Generation and
     surfaced in the API, UI, eval and benchmark JSON. Found that the eval's
     99.9% hit rate was an artefact of re-running the same questions against a
     long-lived llama.cpp cache; cold/warm measurement moved to E3.

 E3  Prompt/KV cache A/B  -> DONE (see ENTRY E3)
     Result: repeated query cache hit 0% -> 99.9%, prompt-eval 3,631 ms ->
     148 ms (-95.9%), end-to-end 32.4 s -> 26.5 s (-18.0%, noisy, n=3/2).
     No benefit for a genuinely new prompt (cold hit 0%). Cache remains on by
     default; report as a repeat-query optimization.

 E4  Rewrite cache (normalized query -> rewrite)
     Expected hit saving: ~2,142 ms mean rewrite time (8.0% of E2E).
     Guardrail: rewrite quality unchanged; cache key must include model/config.

 E4  Rerank cache (query + candidate ids -> scores)
     Expected hit saving: ~1,541 ms (the largest retrieval-side win).
     Guardrail: NDCG/manual relevance unchanged; invalidate on reranker change.

 E5  Embedding cache (normalized query -> 1024-d vector)
     Expected hit saving: ~56-290 ms depending on path.
     Guardrail: vector fingerprint/model/dimension must be part of the key.

 E6  Retrieval cache (filters + rewritten query -> fused candidates)
     Expected hit saving: ~200 ms; mostly useful for repeated benchmark/demo
     queries. Guardrail: ACL and index fingerprint in the key.

 E7  Answer cache (query + filters + ACL + prompt version -> full AskResult)
     Near-zero latency on hits, but highest risk: ACL/session isolation, stale
     answers, feedback semantics. Only pursue if repeat traffic justifies it.

 E8  Context budget tuning (6,500 -> 4,000 tokens)
     Expected: lower prompt-eval time and generation input; risk of losing
     evidence. Guardrails: answer rate, grounding, citation validity, manual
     spot-check on the 12-question set.

 E9  Reranker optimization (batch size, max_length, ONNX/quantization)
     Target: reduce the 1,541 ms retrieval-only rerank cost by 30-50%.
     Guardrail: rerank lift / relevance must not collapse. CPU fallback is
     deliberately off (~9 s per candidate), so do not use it as a speedup.

 E10 Output guard optimization (cache source embeddings, batch checks)
     Target: cut the 548-853 ms output-guard cost by ~50%.
     Guardrail: same block/allow decisions on the labelled set.

 E11 Parallelize independent work
     Input guard + history load are independent; rewrite must precede retrieval.
     Expected saving: a few hundred ms at most. Measure, do not assume.

 E12 Generation optimization (the only large E2E lever)
     Options: streaming TTFT, concise-answer prompt, max-token cap, speculative
     decoding in llama.cpp. Guardrail: answer completeness and grounding.
     Any 10%+ E2E claim will come from here, not from retrieval caching.

 Reporting rule: E1 changes a metric definition/status; do not present it as an
 accuracy improvement in a resume. E3-E7 only help repeated queries - report the
 cache hit rate alongside the hit latency, otherwise the "speedup" is misleading.
